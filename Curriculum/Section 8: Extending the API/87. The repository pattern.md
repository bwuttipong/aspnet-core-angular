A Repository  mediates between the domain and data mapping layers, acting like an in-memory domain object collection.

**What we are doing right now**

Web Server

       ^


Controller       < >       DbContext

                                ^

Repository   //             Database

Abstraction from Dbcontext


### Encapsulates the logic

DbContext   >>  I suppoert the following methods:
                Users.First()
                Users.FirstOrDefault()
                Users.SingleOrDefault()
                Users.Include(x=>x.Thing).FirstOrDefault
                + another 10000 methods

Repository  >>  I support the following 4 methods:
                GetUser()
                GetUsers()
                UpdateUser()
                SaveAll()


### Reduces Duplicate query logic


**UserControler**

```csharp
var user = context.Users.Include(x => x.Thing).FirstOrderDefault(x => x.UserName == username);
```

**MessageController**

```csharp
var user = context.Users.Include(x => x.Thing).FirstOrDefault(x => x.UserName == username)
```

**LinkesController**

```csharp
var user = context.Users.Include(x => x.Thing).FirstOrDefault(x => x.UserName == username)
```

**Repository**

```csharp
publce User GetUser(string username) {
    return context.Users.Include(x => x.Thing).FirstOrderDefault(x => x.UserName == username);
}
```

### Advantages of Repository Pattern
**Minimizes duplicate query logic**
**Decouples application from persistence framework**
**All Database queries are centralised and not scattered throughout the app.**
**Allows us to change ORM easily**
**Promotes testablility**
**We can easily Mock a Repository interface, testing against the DbContext is more difficult**

### Disadvantages of Repository Pattern

**Abstraction of an abstraction**
**Each root entity should have it's own repository which means more code**
**Also need to implement the UnitOfWork pattern to control transactions**
